# 故障复盘：rocm_dev 容器把整台机器拖死（2026-11-03 ~ 11-06）

> 结论速览：**不是容器的锅，是 VS Code 的 Dev Containers 扩展 + `network_mode: host`
> 构成的端口转发自激循环**，在容器里每秒 fork 一个永不退出的 `node -e` 桥，
> 最终 1000+ 孤儿进程、14~16G 内存、8000+ 任务，把 31G 内存的机器拖到 swap 打满、
> 整机卡死。另有两条独立的次要故障（无内存上限、IPC socket 权限），叠加放大伤害。

---

## 一、用户视角症状（原始描述）

- 机器 31G 内存 + 31G zram swap，容器 `rocm_dev` 会"莫名其妙"占掉 20G 左右内存；
- 占满之后**整个系统卡死**，只能硬重启/重启容器；
- 重启后立刻恢复正常，"默认不会这样，但触发某个行为后内存会一直涨"；
- 关键补充：**用终端 `docker exec` 进容器没问题，只要用 VS Code 连进去才会出事**；
- 后来收紧内存上限后，变成"容器不会被杀，但整机被拖死、连对话都卡住"。

## 二、关键证据（按发现顺序）

### 1. 整机 OOM 的凶手是 systemd-oomd，不是容器自己崩

```bash
journalctl -b 0 | grep -E 'oomd|Marked /system.slice/docker'
```

```
22:00:36  Marked docker-2069db3c….scope for killing due to
          memory used (30141612032) / total (33425391616)
          and swap used (33422520320) / total (33424404480) being more than 90.00%
22:00:37  docker-2069db3c….scope: systemd-oomd killed 12581 process(es) in this unit
```

一晚上 6 次（22:00 / 22:04 / 22:25 / 22:31 / 22:34 / 22:58）。

特征判据：`docker inspect` 里 `ExitCode=137` 但 **`OOMKilled=false`**
—— 这是"外部（oomd）整组杀"，不是 cgroup 内部 OOM。

### 2. 容器当时没有任何内存上限

```bash
docker inspect rocm_dev --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}'
# 0 0
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.max
# max          ← 容器内任何进程都能吃光整机
```

### 3. VS Code 的 IPC socket 建不出来（EACCES 崩溃循环）

```
22:14:30 [error] ServerAgentHostManager: agent host failed to start
         listen EACCES: permission denied /run/user/1000/vscode-ipc-e3e5e639-…
22:14:33 [error] agent host failed to start, giving up after 5 restarts
22:14:41 [info]  [AgentHostChannel] Renderer requested connect to upstream
22:14:42 [error] agent host failed to start …       ← 又从头来，直到容器被杀
```

原因：compose 只挂了**单个** wayland socket，容器内 `/run/user/1000` 是镜像自建的
`root:root 0755`，uid 1000 写不进去。

### 4. 真正的内存曲线：不是"某进程泄漏"，是进程数爆炸

```
23:01:05  cur=3.21G  tasks=1001
23:01:41  cur=9.39G  tasks=4418
23:02:18  cur=14.92G tasks=7897
23:02:23  cur=15.82G tasks=8417     ← 每 5 秒 +500 个任务
```

同一时刻 RSS 前 5 名加起来只有 2.3G，`memory.stat` 里：
`anon=14.8G  kernel_stack=145M  pagetables=722M`
—— 典型"几千个线程/进程把内存摊平"，不是单进程泄漏。

### 5. 点名到具体命令（探针按"同一命令行重复份数"统计）

```
COUNT 1196 x /home/rocmUser/.vscode-server/bin/<commit>/node -e '
    const net = require('net');
    const client = net.createConnection({ host: '127.0.0.1', port: 33173 }, ...)
    client.pipe(process.stdout); process.stdin.pipe(client); ...'
```

### 6. 父进程追查：它们都是孤儿，真正的拉动者是 Dev Containers

```bash
# 694 个隧道进程，父进程全是 containerd-shim（即容器 PID 1）——说明原始父进程早就退出
隧道进程数: 694   端口分布: {'33173': 694}
父进程 390465 → 694 个子隧道  (containerd-shim-runc-v2 …)
```

`127.0.0.1:33173` 的监听者 = **容器内 VS Code server 自己的 stream 服务**：

```
LISTEN 127.0.0.1:33173  users:(("MainThread",pid=393774,fd=21))
393774 ← out/server-main.js   ← bin/code-server
```

### 7. 决定性证据：宿主侧 Dev Containers 日志

```bash
grep -E 'Port forwarding connection from' \
  ~/.config/Code/logs/<ts>/window1/exthost/ms-vscode-remote.remote-containers/remoteContainers-*.log
```

```
[15:06:01.409Z] Port forwarding connection from 35380 > 40321 > 33173 in the container.
[15:06:01.516Z] Port forwarding connection from 35386 > 40321 > 33173 in the container.
…  每秒 135 条；1159 次连接里只有 4 次正常 terminated
[15:07:31.897Z] Port forwarding 56740 > 40321 > 33173 terminated by extension (closed) with code 127
```

格式是 `客户端临时端口 > 宿主转发端口 > 容器内端口`：
**Dev Containers 把容器内 33173（VS Code server 自己的内部端口）当成"要自动转发的服务"**，
而 `network_mode: host` 让".转发出去的端口"在容器里也是 `127.0.0.1`——
于是转发出去又被自己连回来，一个连接变成无限个连接。

## 三、被推翻的假设（留档，避免后来者重走）

| 假设 | 为什么看起来像 | 为什么被推翻 |
|---|---|---|
| 显存泄漏 / ROCm GTT | 容器名带 rocm，跑 RL 训练 | `mem_info_vram_used` 只有 116MB，GTT 111MB，完全是主机内存问题 |
| 页缓存被 57G 工作区扫描灌满 | 有一次确实看到 `23.6G peak + 21.3G read / 4min, 1M written` | 那次是另一条路径（大目录扫描）；但主症状的 `anon` 占 14G、`file` 只 0.05G，是进程风暴不是页缓存 |
| Jupyter / SB3 / MakeVecEnv 泄漏 | `main.py` 有 `while True: render("human")`，ipython 历史里有 `make_vec_env` | 崩溃时刻 jupyter 内核根本不在运行；用户也确认终端进容器不复现 |
| Fitten Code token 过期导致 | 日志里 `fittencode.tokenExpired` 反复刷屏，`~/.fittencode/agent-linux-x64` 也在读盘 | 计数只有 23 次/7 秒；隧道进程与它无父子关系。**是噪声，不是原因** |
| 容器镜像/容器本身有问题 | "容器把系统搞崩了" | 镜像里没有常驻服务；`docker exec` 交互完全正常；一切只发生在 VS Code 连上之后 |

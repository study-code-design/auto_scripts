## A. 仓库内的改动（`auto_scripts/rocm-docker/`）

| # | 文件 | 改了什么 | 原因（现象 → 机制） | 解决办法 | 怎么验证 | 现状 |
|---|---|---|---|---|---|---|
| 1 | `docker-compose.yml` | 新增 `mem_limit: 24g` + `memswap_limit: 24g` | 容器 cgroup `memory.max = max`（无上限）→ 容器内任何进程都能吃光整机 31G RAM + 31G zram swap → `systemd-oomd` 按 `SwapUsedLimit=90%` 触发**整组杀**，一次杀掉 1.2 万个进程（`ExitCode=137` 但 `OOMKilled=false`） | 给容器硬上限 24G，且 `memswap_limit == mem_limit`（不给容器 swap，避免顶满整机 zram）；超限时只杀容器内最胖的那个进程 | `cat $CG/memory.max` → `25769803776`；`cat $CG/memory.swap.max` → `0` | ✔ 生效 |
| 2 | `docker-compose.yml` | volumes 里把「只挂单个 wayland socket」改成「整目录挂 `${XDG_RUNTIME_DIR}:/run/user/1000`」 | 只挂单 socket 时，容器内 `/run/user/1000` 由镜像建成 `root:root 0755`，uid 1000 写不进去 → VS Code 建 `vscode-ipc-*.sock` 报 `EACCES` → `ServerAgentHostManager` 五次重启后放弃、再被拉起，**无限崩溃循环** | 挂宿主真实目录（`fiz:fiz 0700`），容器内同 uid 即可写 | `docker exec rocm_dev touch /run/user/1000/_p` 成功；日志里 `agent host started` + `Opening upstream to /run/user/1000/vscode-ipc-….sock` | ✔ 生效 |
| 3 | `.env` | `WAYLAND_DISPLAY=wayland-0` → `wayland-1` | 宿主实际 socket 是 `wayland-1`（`ls /run/user/1000 | grep wayland`），配置写错导致 GUI/挂载指向不存在的路径 | 改成宿主真实值 | 容器内 `echo $WAYLAND_DISPLAY` 且 `/run/user/1000/wayland-1` 存在 | ✔ 生效 |
| 4 | `Dockerfile.dev` | 注释掉 `RUN curl … zoxide … install.sh \| sh` | 装到 `/home/rocmUser/.local/bin`，而 `/home/rocmUser` 是 `rocm-home` volume —— **运行时被完全遮蔽，装了也用不上**；且每次 build 都要访问 `github.com/…/releases`，没开代理**必失败**（实测 exit 1） | 注释掉并写明原因；需要时取消注释（zoxide 0.9.4 本来就在 volume 里） | `docker build -f rocm-docker/Dockerfile.dev -t rocm6-4_ub22:latest .` 能过；容器内 `zoxide --version` 仍有输出 | ✔ 生效 |
| 5 | 新增 `tools/memwatch.py`<br>新增 `tools/rocm_hog_watch.sh`<br>新增 `tools/rocm_guard.sh`<br>新增 `tools/install-units.sh` | 取证探针 + 观察器 + 保险丝 + 一键装服务 | 故障期间**没有任何历史数据**：`docker stats` 只给一个总数，`systemd-oomd` 只报一个 cgroup，无法回答"谁在吃"。排查被迫反复复现 | `memwatch.py` 直接读 `/proc` 输出：内存曲线、**线程数 top**、**同一命令行重复份数 + 父进程 + 祖父进程**、RSS top；guard 超阈值**先取证再 `docker kill`** | `python3 tools/memwatch.py $CG --report` | ✔ 可用 |
| 6 | 新增 `AGENTS.md`、`CHANGELOG-2026-11.md`、`docs/01~03`、`tools/README.md` | 交接文档 | 这次踩的坑有两个特点：①症状极具误导性（像显存/像泄漏）②同一个坑会被下一个人重走 | 记录 7 条证据原文、**5 个被推翻的假设**、三层根因、复发排查手册、允许/禁止改动清单 | 读 `AGENTS.md` 第 0 节的阅读顺序 | ✔ 已提交 |

## B. 仓库外的改动（换机器/重装时必须手动补）

| # | 位置 | 改了什么 | 原因（现象 → 机制） | 解决办法 | 怎么验证 | 现状 |
|---|---|---|---|---|---|---|
| 7 | 宿主 `~/.config/Code/User/settings.json` | `"remote.autoForwardPorts": false`<br>`"remote.restoreForwardedPorts": false` | **主因**。Dev Containers 自动把容器内监听端口 `33173`（= 容器内 VS Code server 自己的 stream 服务）当"要转发的服务"，在宿主开 `127.0.0.1:40321 → 容器:33173`。因为 `network_mode: host`，容器里的 `127.0.0.1` 就是宿主的 `127.0.0.1` ⇒ 转发链能自己连自己 ⇒ 每秒 ~135 次连接，每次都 `docker exec` 起一个**永不退出**的 `node -e` 桥（1159 次里只有 4 次正常结束）⇒ 1200+ 孤儿进程 / 14G anon / 8417 tasks ⇒ 整机卡死 | 关掉自动端口转发；需要时在 PORTS 面板手动 "Forward a Port" | `grep autoForwardPorts ~/.config/Code/User/settings.json` → `false`；宿主 `remoteContainers-*.log` 里 `Port forwarding connection from` 从每秒 135 条降到个位数 | ✔ 生效 |
| 8 | 容器内 `~/.vscode-server/data/Machine/settings.json` | 加 `files.watcherExclude`(19) / `search.exclude`(19) / `python.analysis.exclude`(13) / `search.followSymlinks: false` | 工作区 **57G**（RLDog 17G、RL_project 16G、tools 5.2G、ros2_project 4.1G）+ `~/.cache/uv` **20G**，一条排除规则都没有 ⇒ watcher / 全局搜索 / Pylance 索引全量裸扫。曾观测到 `23.6G peak + 21.3G read / 4min + 1M written` ⇒ 页缓存灌满上限后进入"回收→重读"抖动 ⇒ 整机 I/O 卡死（这是**另一条**独立的伤害路径） | 排除 `.venv/.cache/node_modules/site-packages/__pycache__/build/install/log(s)` 与 `*.zip/tar/tar.gz/bag/h5/npy`；Pylance 同步排除 | `docker exec rocm_dev python3 -c "import json;d=json.load(open('/home/rocmUser/.vscode-server/data/Machine/settings.json'));print(len(d['files.watcherExclude']))"` → 19 | ✔ 生效 |
| 9 | 工作区 `/home/fiz/Documents/project/ros2/workspace.code-workspace` | 修成合法 JSONC（原本结尾多了 `},`），保留全部原设置，并加同样的排除规则 | 文件**非法 JSON** ⇒ VS Code 解析失败 ⇒ 里面所有 settings（包括你配的 `http.proxy`）**从未生效**。这解释了"为什么排除规则一直不存在" | 重写为合法 JSONC | `python3 -c "import json,re;json.loads(re.sub(r'^\s*//.*$','',open(...).read(),flags=re.M))"` 不报错 | ✔ 生效 |

## D. 故障链一图流

```
            ┌─ 第3层（主因）───────────────────────────────────────────────┐
            │ Dev Containers 自动转发容器内 33173                          │
            │        + network_mode: host（容器内 127.0.0.1 == 宿主）       │
            │        ⇒ 自激：每秒 135 次连接，每次 fork 一个不退出 node -e   │
            │        ⇒ 1200 孤儿进程 / 14G anon / 8417 tasks                │
            └───────────────────────────┬─────────────────────────────────┘
                                        │
   第1层：容器无内存上限 ────────────────┼──────▶ 整机 31G RAM + 31G zram 打满
   （放大器）                           │              │
                                        │              ├─▶ systemd-oomd 整组杀 1.2 万进程（ExitCode 137 / OOMKilled=false）
                                        │              │
   第2层：/run/user/1000 不可写 ─────────┘              └─▶ 收紧上限后改为「回收→重读」抖动 ⇒ 容器不退出但整机卡死
   （放大器，制造 EACCES 崩溃循环）

   另一条独立路径：57G 工作区 + 20G uv 缓存无排除规则 ⇒ 21.3G/4min 读盘 ⇒ 页缓存灌满 ⇒ I/O 抖动
```

## F. 一句话给下一个人

> 看到 `rocm_dev` 内存暴涨，**先看 `pids.current` 和"同一命令重复份数"，不要看 RSS 排行**；
> 如果是 `node -e` 刷到成百上千份，去宿主 Dev Containers 日志确认
> `Port forwarding connection from … > … > <容器内端口>` 是否在刷屏，
> 然后检查 `remote.autoForwardPorts` 是否被改回 `true`。
